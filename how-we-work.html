01

Understand the problem deeply

Before we design anything, we learn how the work actually happens. We spend time with staff and the people they serve, map today's workaround, and agree on the one problem worth solving first.

  • Watch the work, don't just ask about it
  • Map the current workaround, warts and all
  • Write the problem in one sentence, together
Staff Community Build Guild

02

Co-create with the people who'll use it

Nonprofit staff and the communities they serve are part of the team, not just the audience. We sketch, test, and decide together, so the tool fits real constraints like budget, connectivity, and time.

  • Working sessions over status updates
  • Sketches and prototypes in hand early
  • Decisions made with the people affected

03

Deliver fast

We keep scope small and teams light, so useful tools reach people in weeks. Our trail field notes app was designed in two days and built in about a week.

  • One problem per project
  • Small volunteer teams, light overhead
  • Working software over long documents
Test in the field Learn Fix Share

04

Validate in the real world

A tool is done when it works for the people using it. We put it in their hands, watch what happens, fix what's off, and publish everything open source so others can reuse it.

  • Test where the work happens
  • Iterate on what we see, not what we assumed
  • Open-source the code and a simple handoff
